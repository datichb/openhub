# Remote execution: installing the GitLab CI runners

An oh session can run on a **GitLab CI runner** instead of your machine. This guide covers the setup: the runner, the central `oh-runner` project of a GitLab group, and `oh remote setup`. Remote execution is available on macOS and Linux; on Windows, oh stays local.

## How it works

```
your machine (oh)                           GitLab                                   runner (Docker)
─────────────────                           ──────                                   ───────────────
oh run … --runtime remote ──bundle──▶ package registry (oh-runner)
                          ──trigger──▶ oh-runner pipeline ─────────────────▶ job: project image
                                                                                oh runner: project clone,
                                                                                opencode + LLM proxy, branch + MR
oh session fetch ◀──artifacts── Beads journal, summary, session export ◀──
```

- **One `oh-runner` project per GitLab group.** Its `.gitlab-ci.yml` is **generated by oh** (`oh remote setup` rewrites it). The projects' own CI is never changed.
- **Your machine's secrets do not leave it.** The job only gets **masked and protected CI variables** of the `oh-runner` project: the jobs' LLM key, one access token per target project, a team-state write token. Your keychain only keeps the GitLab API token (yours) and the trigger token.
- **Beads stays on your machine.** The job gets a snapshot of the tickets involved and sends back a journal of its writes, which you replay when fetching (with conflict resolution).
- **The job image** is the project's development image (its dev Dockerfile, or a default Debian base) plus a thin layer (oh, opencode, fake `bd`). It is built on the runner and kept in the container registry of `oh-runner`, tagged with its hash.

## What you need

| Item | Details |
|---|---|
| GitLab instance | gitlab.com or self-managed (16.0 or later). **Container registry** and **package registry** enabled (self-managed: enabled by the administrator). |
| Group | You are **Maintainer** (to create `oh-runner`, its variables and its trigger). |
| Runner | A Linux machine (or a Mac with Colima) with Docker and `gitlab-runner`, **Docker** executor, tag `oh`. At least 2 CPUs and 4 GB of memory per concurrent job. |
| Runner network access | GitLab and its registry; `registry.npmjs.org` (Linux opencode binary); `github.com` (released oh binary); the LLM provider (e.g. `bedrock-runtime.eu-west-1.amazonaws.com`); the registries of the base images (Docker Hub, `gcr.io` for Kaniko). |
| Personal token | `api` scope, on your account: used by oh from your machine (setup, bundle upload, tracking, artifacts). |
| Token of each target project | **Project** access token, Developer role, `write_repository` and `read_api` scopes: the job clones, pushes the branch and opens the MR (as a draft, through `git push` options, without the `api` scope). |
| Team-state token | Access token of the team-state repository, `write_repository` scope: the job publishes progress in the ticket claim. |
| Jobs' LLM key | A key dedicated to CI. For Bedrock: a long-term **Bedrock API key** (region `eu-west-1`); your machine's AWS profiles cannot be used in a job. Anthropic and OpenRouter: an API key. |

## 1. Install the runner

### Create the runner in GitLab

Group › **Build › Runners › New group runner** (gitlab.com or self-managed):

- **Tags**: `oh`;
- untick "Run untagged jobs";
- keep the displayed `glrt-…` token.

An instance runner also works (self-managed), as long as it has the `oh` tag and is available to the `oh-runner` project.

### Install `gitlab-runner` on the machine

Linux (Debian/Ubuntu):

```bash
curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash
sudo apt-get install gitlab-runner
```

macOS with Colima:

```bash
brew install gitlab-runner colima docker
colima start --cpu 4 --memory 8
brew services start gitlab-runner
```

### Register the runner

Pick how the project image is built:

- **Kaniko** (default, recommended): no privileged mode.

  ```bash
  sudo gitlab-runner register --non-interactive \
    --url https://gitlab.example.com \
    --token glrt-XXXXXXXX \
    --executor docker \
    --docker-image alpine:3.20 \
    --description "oh runner"
  ```

- **Docker-in-Docker**: the runner must be **privileged**, which gives the job control of the machine's Docker daemon. Keep it for a dedicated machine.

  ```bash
  sudo gitlab-runner register --non-interactive \
    --url https://gitlab.example.com \
    --token glrt-XXXXXXXX \
    --executor docker \
    --docker-image docker:27 \
    --docker-privileged \
    --docker-volumes /certs/client \
    --description "oh runner (dind)"
  ```

  Then `oh remote setup --builder dind`.

In `/etc/gitlab-runner/config.toml` (or `~/.gitlab-runner/config.toml` on macOS), set `concurrent` according to the available memory (one job ≈ 1 to 2 GB).

Check: `sudo gitlab-runner verify`; the runner then shows as "online" in GitLab.

Architecture: an arm64 runner (Apple Silicon Mac, Graviton) works; declare it with `oh remote setup --arch arm64`.

## 2. Create the tokens

1. **Personal token** (`api`): Preferences › Access tokens.
2. **Token of each target project**: project › Settings › Access tokens › **Developer** role, `write_repository` and `read_api` scopes.
3. **Team-state token**: team-state repository › Settings › Access tokens › **Developer** role, `write_repository` scope.
4. **Jobs' LLM key** (e.g. a Bedrock API key created in the AWS console, limited to Bedrock).

Never paste them in a command: `oh remote setup` asks for them with hidden input, or reads them from an environment variable (`--token-env`, `--llm-key-env`, `--project-token-env`, `--teamstate-token-env`).

## 3. Configure oh: `oh remote setup`

From a project of the group (the instance and the group are suggested from its `origin` remote):

```bash
oh remote setup --llm --teamstate --project acme/dev/api
```

oh:

1. checks API access with your token (kept in the keychain, key `openhub.remote.<target>.token`);
2. creates the `oh-runner` project in the group if missing (private, registries on), or validates it;
3. checks that its default branch is **protected** (protected variables are only passed to protected branches);
4. writes `.gitlab-ci.yml` (refuses to replace a file not generated by oh, unless `--force`);
5. creates the trigger token and keeps it in the keychain;
6. sets the CI variables: `OH_LLM_PROVIDER`, `OH_LLM_REGION` (not secret), `OH_LLM_KEY`, `OH_PROJECT_TOKEN_<project id>`, `OH_TEAMSTATE_TOKEN` (masked and protected);
7. reports when no runner with the tag is online;
8. saves the target in `~/.oh/hub.toml` (`[[remote.targets]]`, no secret at all).

The command can be run again: only what is missing or changed is modified. Add a target project later with `oh remote setup --project <path>`.

Several teams, several instances: each group has its own target (`--name`, `--url`, `--group`). A project is sent to the target of the same instance whose group contains it (the deepest group wins); to force one, use `[remote.projects]` in `hub.toml` (`<oh project id> = "<target>"`).

### Development builds

A released oh version is downloaded by the job from the GitHub release. For a development build:

```bash
make -C cli build-linux            # ARCH=arm64 for an arm64 runner
oh remote setup --oh-binary cli/bin/oh-linux-amd64
```

The binary is uploaded to the package registry of `oh-runner` (`oh-cli/<sha256>/oh-linux-<arch>`); do it again for each new build.

### Options

| Option | Effect |
|---|---|
| `--tag` | runner tag (`oh`) |
| `--builder kaniko\|dind` | project image builder |
| `--arch amd64\|arm64` | runner architecture |
| `--timeout 3h` | maximum duration of a job |
| `--runner-project` | another path than `<group>/oh-runner` |
| `--token-key` | reuse a token already in the keychain |
| `--no-create` | do not create `oh-runner` |

The same settings are shown in the TUI: **Configuration › Remote**; a change is applied to the pipeline by the next `oh remote setup`.

## 4. Check: `oh remote status`

```bash
oh remote status
```

Shows, per target: API access, project, registries, protected branch, pipeline up to date, trigger token, missing variables, online runners, oh binary for the job. `oh doctor` (and the Doctor view of the TUI) runs the same check.

## 5. Start a remote session

```bash
oh run ticket -t bd-42 --runtime remote
```

Before sending, oh checks that:

- the workflow allows `remote` (`runtime.allowed`) and no checkpoint that waits for approval in the chosen mode is `remote: forbid`;
- the project is on a **pushed** branch: the job starts from the remote branch (uncommitted changes are not sent, a warning says so);
- the dev Dockerfile, if any, is committed on that branch;
- the `oh-runner` pipeline is the one of this oh version.

Then, for each session:

1. **reservation** of the tickets: `bd update <id> --claim` on your machine and a claim in the team-state (refused when another member holds it);
2. **Beads snapshot** of the tickets, their dependencies and their children (`beads-snapshot.json`), with the revision of each to detect conflicts on return;
3. **upload** to the package registry of `oh-runner`: the session bundle by its hash (`oh-bundle/<hash>`, uploaded once) and the session envelope (`oh-session/<hash>`: prompt, inputs, checkpoint policy, snapshot);
4. **trigger** of the pipeline; the session shows in `oh session list` (☁) and progress in the ticket claim.

When the trigger fails, the reservations made by oh are undone. `--headless` does not apply to remote runs.

Checkpoint policy in the job (never blind approval): `remote: auto` is approved by oh's policy responder; `remote: defer` stops the session cleanly once the MR is ready, the rest happens locally after fetching.

## 6. In the job: `oh runner`

The `oh-run` job runs `oh runner run` in the project image:

1. **Fetch** of the bundle and of the session envelope with the job token (`CI_JOB_TOKEN`), checked by their hash.
2. **Clean-up** of the environment: every secret variable (LLM key, tokens, `CI_JOB_TOKEN`, registry passwords) is removed from the process before anything is started.
3. **Clone** of the project with its token (`OH_PROJECT_TOKEN_<id>`, passed through git's environment, never in a URL or a file) and creation of the session branch.
4. **Session**: same code as on your machine — oh daemon, credential proxy (sole holder of the LLM key), opencode server and "closed world" bundle. The opencode server runs as the `oh` account (created in the image), which can read neither the job processes, nor the oh database, nor the secrets.
5. **Policy responder** (never blind approval):

   | Request | Answer |
   |---|---|
   | checkpoint `remote: auto` | approved |
   | checkpoint `remote: defer` | the session stops cleanly: branch and MR pushed, continued locally |
   | other permission (`ask`) | refused, with a message to the agent |
   | agent question | the session stops ("question pending"), resumed locally |
   | error, budget, circuit breaker | the session stops (failed) |

6. **Beads**: `bd` is oh's fake bd; it goes through the Beads gateway of the job's daemon, which applies `beads.allow`. Reads come from the snapshot; writes are recorded in `journal.jsonl` (and seen by later reads), then replayed on your machine when fetching.
7. **Branch and MR**: what is not committed gets committed, the branch is pushed and a **draft MR** is opened through `git push` options. Progress is published in the ticket claim (`OH_TEAMSTATE_TOKEN`).
8. **Artifacts** (`oh-out/`, 7 days): `journal.jsonl` (Beads writes), `summary.json` (outcome, cost, decisions, MR, outputs), `session.export` (transcript of the session and its sub-agents, to resume it locally).

Limits: MCP servers that need a token of your machine (gitlab, jira, figma…) are not available in the job; oh's `workflow` server is. When the job is canceled or times out, the session is exported and the work pushed before stopping when possible.

## 7. Follow, fetch, replay

**Following.** `oh session list` and the Sessions view of the TUI check the pipelines (every 30 s in the TUI): the ☁ session is "Running" (pipeline pending or running), then moves to **"To fetch"** once the pipeline is over (or failed: its artifacts can still be fetched). A system notification says so. Progress is also visible to the team in the ticket claim.

**Fetching** — `oh session fetch <id>` or `g` in the Sessions view:

1. download of the artifacts of the `oh-run` job (`journal.jsonl`, `summary.json`, `session.export`) to `~/.oh/sessions/<id>/remote/`;
2. summary: outcome (completed, deferred checkpoint, question, failed), cost, MR, requests refused by the policy;
3. **import of the session** (and its sub-agents) into a local server, in a worktree of the branch pushed by the job: `oh session attach <id>` resumes it where it stopped (deferred checkpoint to approve, question to answer, rest of the work).

`--no-import` only downloads the artifacts.

**Replaying the Beads journal** — `oh session resolve <id>` or the TUI window:

- every write is **checked again** on the machine (workflow `beads.allow`, refused options, job files, tickets of the session); the others are refused;
- a ticket **changed on the machine since sending** (its revision changed) is a **conflict**: for each, *Keep local* (nothing applied to that ticket), *Apply remote* (all its writes), *Merge the notes* (notes and comments only);
- **nothing is applied without confirmation**; tickets created in the job get their real id and the following writes use it;
- can be run again: a failed write is retried, the others are not replayed.

```bash
oh session resolve <id> --dry-run                 # see the replay
oh session resolve <id> --merge-notes bd-40 --yes # without a terminal
```

## The generated pipeline

Three jobs, triggered **only** by oh (never on push):

| Job | When | Role |
|---|---|---|
| `oh-cli` | image missing from the registry | fetches oh (release checked against `checksums.txt`, or development binary checked by its SHA-256) and prepares the oh layer |
| `oh-image` | image missing from the registry | builds the base image (dev Dockerfile of the project, cloned with the project token; otherwise Debian + git + ripgrep) then the oh layer, and pushes them |
| `oh-run` | always | `oh runner run` in the project image; artifacts in `oh-out/` (7 days) |

The trigger variables (session id, project, branch, bundle and image addresses) are not secret: they are visible in the pipeline page.

## Security

- Secret variables are **masked** (absent from logs) and **protected** (default branch of `oh-runner` only). Limit the Maintainers of `oh-runner`: they can read these variables.
- The LLM key is only read by oh's credential proxy in the job; opencode only gets a session token.
- Project tokens have the minimal scope: repository (read/write) and API read; the MR is opened through `git push` options.
- Kaniko needs no privileged mode; Docker-in-Docker does, keep it for a dedicated machine.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `Protected branch — failed` | Protect the default branch of `oh-runner` (Settings › Repository › Protected branches). |
| `Online runners — to check` | Runner stopped, without the `oh` tag, or not available to `oh-runner`. |
| `Container and package registries — failed` | Registries disabled on the project or the instance. |
| `CI variable — failed — OH_LLM_KEY` | `oh remote setup --llm`. A value shorter than 8 characters or on several lines cannot be masked by GitLab. |
| `oh-image` job: `OH_PROJECT_TOKEN_<id> is missing` | `oh remote setup --project <project path>`. |
| `oh-cli` job: download failed | The runner cannot reach `github.com`: upload the binary with `--oh-binary`. |
| `Generated pipeline — failed` (file not generated by oh) | Hand-written `.gitlab-ci.yml`: `oh remote setup --force` replaces it. |
