# 05 — Phase 1 : workflows multiples déclaratifs

## Objectif
Chaque cas d'usage devient un **workflow YAML** (`oh/v1`) livré par le hub ; lancement par `oh run <wf>` et par la **fiche de lancement** générée dans la TUI ; les anciennes commandes deviennent des alias. Le paquet de session est désormais compilé **à partir du workflow résolu**.

## Prérequis
Phase 0 terminée. Lire `03` §3–§4, `10` §1–§6, `13` §2, §7.

## Critères d'acceptation
1. `oh run ticket --tickets bd-1,bd-2` ouvre 2 sessions (1 serveur, 2 worktrees) ; chaque session ne voit que les agents/skills de `ticket`.
2. `oh bundle show cadrage --budget` affiche agents, skills (fermeture), permissions, budget ; comparaison avec l'ancien déploiement complet (O19) consignée.
3. Les anciennes commandes fonctionnent via alias, avec avertissement.
4. TUI : « Démarrer » remplace le lancement rapide sur les 3 accueils ; fiche générée pour chaque workflow livré ; sélecteur Beads tview ; épinglage.
5. Validation : erreurs lisibles (chemin + message) pour cycles, agents inconnus, variables de prompt inconnues, `risk: read` avec agent qui écrit.
6. `orchestrator.md` ne contient plus de modes A–E.

## Hors périmètre
Édition/publication de workflows (phase 2), vue Sessions et décisions (phase 3), conteneur (4), distant (5).

### Piste A (moteur)
- **Lot 1 (P1-T02 → T05), décisions du 05/10** : un assouplissement de sécurité est une **erreur bloquante** (pas ignoré) ; un workflow de même id dans une couche plus spécifique **doit étendre** le workflow de la couche inférieure la plus proche (`shadow_without_extends`, `must_extend_nearest` : aucune couche ne peut sauter les règles de celle du dessous) ; **verrous (`Enforced`/🔒) reportés en phase 2** (champ additif à ajouter avec la publication) ; `oh workflow validate` livrée par la piste A.
- **Contrat des gabarits de prompt (pour la piste E)** : entrées au premier niveau (`{{ .ticket }}`), contexte de session sous `.oh` : `project`, `location`, `mode`, `runtime`, `lang`, `workflow` (`workflow.OhVariables`). L'id d'entrée `oh` est réservé ; les ids d'entrée sont `^[a-z][a-z0-9_]*$` (champs de gabarit Go, pas de kebab-case). Les fonctions de gabarit ne sont pas vérifiées (le moteur de rendu les définit) ; dans `range`/`with`, seuls `$.x` sont vérifiés. Une valeur par défaut peut référencer d'autres entrées (pas elle-même). Le gabarit est lu **relativement au dossier du fichier YAML** (hub : `<hub>/workflows/prompts/…`, chemin sans `..`).
- **Layout hub attendu (piste E)** : `<hub>/workflows/<id>.yaml` (nom de fichier = id, sinon `id_filename_mismatch`), chargé par `hubcat.LoadWorkflows(hubDir)`. L'embarquement de `workflows/` dans `hubcontent` reste à faire par E. Vérification : `oh workflow validate --all [--json]`.
- **API** (`internal/workflow`) : `Parse/ParseFile/ParseFS → (*Document, Diagnostics)` ; `MemCatalog` (`Add`, `Put`, `LoadFS`, `LoadDir`, `Refs`) derrière l'interface `Catalog` (team-state en phase 2) ; `ResolveSpec(cat, ref, *SessionOptions) → *Resolved{Spec, Chain, Origins, Mode, Runtime, Inputs}` ; `(*Resolved).Validate(Env)` ; `Check(cat, ref, opts, env)` = les deux. `Env{Agents, Skills, Prompts, Isolation}` : interfaces facultatives (règle sautée si absente). `internal/workflow/hubcat` : implémentation sur le hub (frontmatter + permissions résolues des agents ; sous-paquet pour éviter le cycle `deploy → workflow`).
- **`Diagnostic{Severity, Code, Path, Source, Pos{Line,Col}, Message, Hint}`** : `Code` et `Pos` ajoutés à la forme prévue ; messages i18n `workflow.diag.<code>` (+ `.hint`), test qui vérifie que chaque code a sa traduction. Les diagnostics de validation pointent vers le **document qui a posé la valeur** (origine), pas vers la feuille.
- **Colonnes** : yaml.v3 ne donne que la ligne ; la colonne est retrouvée dans l'arbre `yaml.Node` (clé inconnue, valeur mal typée, clé en double). Erreurs de **syntaxe** YAML : ligne seulement. Les erreurs des `UnmarshalYAML` maison (`OrderedMap`, `LocalizedText`, `PluginRef`) passent par `yaml.TypeError` : toutes les erreurs du fichier sont collectées (avant : arrêt à la première). Comportement seulement, schéma inchangé.
- **P1-T03** : `WorkflowOverride` **n'est pas étendu** : le patch est un document `Spec` (P1-T01) ; `override.go`/`Resolve` (ancien modèle) restent pour la compatibilité jusqu'à P2-T11. La **présence** d'un champ dans le fichier (pas sa valeur) décide du remplacement (`required: false`, `mandatory: false` s'appliquent). Cartes fusionnées champ par champ : `inputs.<id>` (+ `picker`), `agents.<id>`, `checkpoints.<id>` (+ `mode` par mode), `modes`, `models` (+ `agents`), `skills`, `runtime`, `circuit_breaker`, `limits`, `entry` ; tout le reste (listes, textes localisés, `prompt`) remplace en bloc. Désactiver l'agent d'entrée = erreur (`entry_disabled`) ; retirer un checkpoint inexistant = avertissement.
- **P1-T04, valeurs effectives d'un champ absent** : `runtime.allowed` absent = `[runtime.default || local]` ; `remote` absent = `defer` ; comportement absent pour un mode = `pause` (avertissement) ; `modes.allowed` absent = `[manuel, semi-auto, auto]` ; `beads` absent = **sans restriction** (comportement actuel ; d'où l'erreur `read_beads_unrestricted` pour `risk: read`) ; `isolation` absent = `standard`. Rangs de durcissement : `risk` read < write < publish ; `remote` auto < defer < forbid ; comportements d'un checkpoint **obligatoire** skip < auto < conditional < pause ; `runtime.allowed`/`beads.allow` sous-ensembles ; `limits.budget_usd` ne peut que baisser. `code_mode`, `mcp`, `plugins` ne sont pas des champs de sécurité (non durcis).
- **P1-T04, couches** : `hub < team < project < session`. Les brouillons ne sont pas une couche mais une source (`Source.Draft`, phase 2). La couche session (`SessionOptions{Mode, Runtime, Inputs}`) vérifie mode/runtime autorisés, entrées connues, typées (les chaînes de la ligne de commande sont acceptées : `"true"`, `"3"`, `"a,b"`) et obligatoires ; elle n'apparaît pas dans `Origins`.

Un mode intégré non autorisé (`auto` alors que `allowed: [manuel, semi-auto]`, cas de l'exemple figé) peut garder son comportement (repris par un patch qui le réautorise) ; un mode inconnu est une erreur. `risk: read` : un agent « écrit » si une des clés `edit/write/patch` n'est pas refusée (clé absente = autorisée par l'outil) ou si son shell n'est pas restreint (`bash` absent, `allow`, ou carte sans `"*": deny`) ; sous-commandes Beads d'écriture : `create, update, close, reopen, delete, edit, comment, label, dep`.
