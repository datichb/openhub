## Lot F2 — renforcement

**(1) Clé du journal chiffrée pour le job**
- Mécanisme (stdlib) : paire **X25519** par cible (`crypto/ecdh`) ; à l'envoi, clé éphémère + ECDH, **HKDF-SHA256** (`crypto/hkdf`, sel = clé éphémère ‖ clé du destinataire), **AES-256-GCM** avec données associées `oh-remote-journal-key/1 \0 <session>` (`remote.SealJournalKey`/`OpenJournalKey`). `Manifest.JournalKeySealed` remplace `JournalKey` ; **`ManifestSchema` 3** ; un champ `journal_key` (forme 2) est refusé par le job avec « update oh … run oh remote setup ».
- Clé privée : variable `OH_JOURNAL_KEY` (base64 sans remplissage, masquable), masquée, protégée, portée `oh-run/*` ; lue par `ReadJob` (obligatoire) avant `ScrubEnv`, ajoutée aux valeurs expurgées ; déchiffrement dans `runner.Fetch` → `Fetched.JournalKey` (mémoire seulement) ; échec ⇒ job en échec avant toute session (« … run oh remote setup »).
- **Écart avec la proposition « clé publique générée par setup »** : la clé publique n'est pas dans `hub.toml` mais **dans le dépôt `oh-runner`** (`oh-journal-key.pub`, branche par défaut protégée), lue à chaque envoi comme `.gitlab-ci.yml` : tous les membres (y compris Developers, qui ne peuvent pas lire les variables) chiffrent pour la même paire, et un `oh remote setup` d'un autre membre **garde** une paire complète (sinon il casserait les sessions en vol des autres). Cohérence vérifiable sans lire le secret : la **description** de la variable porte la clé publique ; paire incomplète ou incohérente ⇒ `oh remote status`/Doctor en échec (étape `journal_key`, clés `cmd.remote.step|hint.journal_key`), `oh remote setup` la recrée. Pas de rotation explicite (supprimer la variable puis relancer setup) : à ajouter si souhaité (`--rotate-journal-key`).
- Migration : **`PipelineSchema` 4** (le fichier CI change aussi pour (2)) ⇒ l'envoi refuse un `oh-runner` non régénéré (« pipeline d'une autre version : oh remote setup ») ; sans paire : `ErrNoJournalKey` → `cmd.remote.send.err.no_journal_key` (fr/en). Sessions envoyées avant : rejeu inchangé (clé dans le trousseau).
- Tests : `TestSealJournalKey` (liée à la session, autre paire, altération, éphémère, alphabet masquable), `TestSetupJournalKeyPair` (création, conservation, paire cassée détectée et recréée, fichier absent), `TestSend` (clé absente en clair de tous les paquets, ouverte par la variable), `TestSendNeedsJournalKeyPair`, `TestFetch` (runner : ouverte en mémoire ; autre paire refusée avec l'indication), `TestReadJob`, `TestRunSealsJournal`.

**(2) Image du job épinglée par empreinte — faisabilité**
- **Kaniko** : `--digest-file` (empreinte du manifeste poussé) — utilisé pour la base et la couche. **DinD** : sortie de `docker push` (`<tag>: digest: sha256:… size: …`), repli sur `RepoDigests` du dépôt de l'image. Les deux scripts vérifient `^sha256:[0-9a-f]{64}$` (sinon le job échoue) et construisent la couche oh **`FROM <base>@<empreinte>`** (une étiquette de base remplacée entre les deux étapes n'est pas reprise).
- Le job `oh-image` publie `oh-image.env` (`OH_RUN_IMAGE=<dépôt>@sha256:…`) en **artefact dotenv** (+ `paths`, pour que la machine le télécharge) ; `oh-run` utilise `image: name: $OH_RUN_IMAGE`. Réutilisation sans build : la machine pose `OH_RUN_IMAGE` en **variable de déclenchement** (priorité sur le dotenv, absent dans ce cas).
- **Point de faisabilité à valider à la recette** : GitLab documente `image:` comme « développé par le Runner avec les variables du job » sans citer le dotenv ; le développement des variables dotenv dans `image:` est constaté par des utilisateurs (gitlab-runner#37361, runner 16.6) mais pas garanti par la doc. Échec fermé : si le runner ne le développe pas, `oh-run` échoue (image vide), il ne retombe **jamais** sur l'étiquette. Option de repli si la recette échoue : deux pipelines (image puis exécution, la machine lit l'empreinte et déclenche le second) — non fait.
- **Écart avec « empreinte transmise dans l'enveloppe scellée »** : l'empreinte n'est pas lue depuis l'enveloppe, parce que l'enveloppe est lue par oh **dans** l'image : une image remplacée contient un oh remplacé, qui ignorerait le contrôle. La référence doit être connue du Runner avant le démarrage du job : variable de déclenchement (posée par la machine seule, jeton de déclenchement) ou dotenv du job d'image du même pipeline (non modifiable par les jobs d'un autre pipeline).
- **Empreinte enregistrée par la machine** : `RemoteRef.ImageBuilt`/`ImageDigest` (colonne JSON `remote_ref`, sans migration) ; relevée par `Track` (passage à `ready`/`failed`) ou `Fetch`, depuis l'artefact du dernier job `oh-image` **réussi** du pipeline (référence vérifiée : même dépôt que l'image de la session, `sha256:` + 64 hex). Réutilisée par l'envoi suivant de la **même image** seulement si l'étiquette désigne encore cette empreinte (`gitlab.RegistryTagDigest`) ; sinon reconstruction + avertissement `cmd.remote.send.warn.image_replaced`. **Changement de comportement** : une étiquette présente mais jamais enregistrée par cette machine n'est plus réutilisée (une construction par machine et par image ; après `oh gc` des sessions, reconstruction).
- Tests : `TestImageJobPinsByDigest` (scripts Kaniko et DinD exécutés avec de faux `executor`/`docker` : couche FROM base par empreinte, dotenv exact ; aussi en debian sous Podman), `TestImageJobFailsWithoutDigest`, goldens régénérés, `TestImageJobsHoldNoSecret` (+ `OH_JOURNAL_KEY`), `TestSend` (pas de `OH_RUN_IMAGE` au build, étiquette non enregistrée ⇒ build, empreinte relevée par `TrackSession`, réutilisation par empreinte, étiquette remplacée ⇒ build + avertissement), `TestImageDigestOf`.
- **Risque résiduel (documenté remote-runners/SECURITY fr/en)** : un projet cible peut encore effacer/remplacer étiquettes et paquets génériques d'`oh-runner` ⇒ déni de service (empreinte refusée, reconstruction), pas d'exécution ; le **reste de l'enveloppe** (prompt, entrées, instantané Beads) reste lisible des membres d'`oh-runner` et des jobs de construction (chiffrer toute l'enveloppe avec la même paire serait simple : non demandé, à décider) ; le `Dockerfile` d'un projet reste de la confiance de ce projet (il s'exécute avec ses jetons) ; empreinte gardée dans `oh.db` (un agent local qui écrirait `oh.db` pourrait la changer — même niveau que les autres données locales) ; Maintainers d'`oh-runner` lisent `OH_JOURNAL_KEY`.
