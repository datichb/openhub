## Piste T — workflow `ticket` fiable

### T1 — Commit et fermeture garantis par oh (A17, A36, A38) — majeures
Problème : le commit et la fermeture du ticket dépendent du modèle (Sonnet commit avant cp-2 ; Haiku jamais, imite cp-2 avec `question`, ferme le ticket sans commit). Une consigne ne suffit pas.
- **Gating par règles de session** (P3-T04 étendu au shell et à Beads) : avant que cp-2 soit **passé** (par `workflow_checkpoint`), refuser `git commit*`, `git push*`, `bd close*` (et `bd update --status done|closed`), **et** les agents verrouillés `after: cp-2` ; ouverture de ces règles au passage de cp-2 (décision `once`). Un checkpoint obligatoire non passé = le travail qui en dépend est **impossible**, quel que soit le modèle.
- **Qui commite** : décider au point de contrôle (proposition : le `developer`, relancé par l'`orchestrator-dev` juste après cp-2 « commit », avec un message conventionnel ; jamais avant). Mettre le contenu (agents, skills d'enchaînement générées, gabarit `ticket`) en accord, **et** retirer des consignes du `developer` le commit autonome.
- **Imitation d'un checkpoint** (A36) : ajouter dans les skills générées une consigne explicite (« les checkpoints passent uniquement par `workflow_checkpoint` ») ; côté oh, le gating suffit à rendre l'imitation inopérante. Option à étudier : refuser l'outil `question` dont le titre/texte annonce un checkpoint (« CP-n ») et renvoyer un message clair à l'agent.
- **Fin de workflow et sorties** (A38) : à la fermeture du dernier ticket / validation du dernier checkpoint, **oh déclare lui-même les sorties** connues (branche courante, tickets fermés, MR si créée) quand l'agent ne l'a pas fait, et marque la session `completed` (pas `sleeping`) ; « Enchaîner avec… » se déclenche alors.
- Tests : e2e Haiku **et** Sonnet sur `ticket` manuel : aucun commit avant cp-2, commit présent après, ticket fermé seulement après le commit, cp-2 imité par `question` sans effet ; unitaires du gating.

### T2 — Hooks git de Beads et faux `bd` (A19, A16) — majeure
- Le faux `bd` laisse passer **`bd hooks run …` quand il est appelé par git** (`BD_GIT_HOOK=1` posé par le hook de bd), en relayant au vrai `bd` par la passerelle (commande ajoutée à une liste interne, pas à `beads.allow`) ; vérifier les autres sous-commandes des hooks (`pre-commit`, `post-merge`, `post-checkout`, `pre-push`, `prepare-commit-msg`).
- **Interdire le contournement des hooks** dans les permissions de tous les agents : `git commit --no-verify*`, `git * -c core.hooksPath*`, `git config core.hooksPath*`, `GIT_CONFIG_*=… git …`, écriture dans `.git/config` (outil d'édition sur `.git/**`).
- A16 : garantir que `bd` résout vers le faux `bd` même si le shell de l'utilisateur réordonne le `PATH` (`~/.zshenv`) — options à proposer au point de contrôle : vérification au démarrage de la session (`command -v bd` dans le shell de session) + avertissement/Doctor ; ou faux `bd` aussi installé sous le nom `bd` dans chaque dossier que le shell met devant (non souhaitable) ; ou règle de permission sur la commande `bd` résolue.
- Tests : contrat `integration` (vrai serveur, vrai démon, vrai `bd`, projet `bd init` avec hooks) : `git commit` passe, `--no-verify` refusé, `.git/config` non modifiable.

### T3 — Commandes Python et garde-fous (A20, A27)
- Liste blanche du `developer` (et `reviewer`, `qa`…) : `python3 -m pytest*`, `python3 -m pip*`, `python3 --version`, `.venv/bin/*`, `uv run*`, `poetry run*` ; vérifier les autres piles (node : `npx`, `pnpm exec` ; go ; ruby `bundle exec`).
- A27 : revoir `universal-guardrails` / frontière de confiance pour qu'une **demande courte de l'utilisateur** (entrée `request`) ne soit jamais traitée comme une injection (seul le contenu externe délimité l'est) ; test e2e Haiku « Dis seulement X ».

## Piste L — lancement et sessions

### L1 — Protéger le travail de l'utilisateur au lancement (A18, A35) — majeure
- Workflow qui **écrit** + dossier choisi **non propre** (modifications non commitées, ou branche d'une autre session) : ne pas lancer sur ce dossier sans choix explicite : **worktree automatique par défaut** (O10 étendu), ou `--location base --allow-dirty` ; fiche de lancement : choix **[w] worktree / [s] mettre de côté (stash) / [b] lancer quand même** dans le Récap (maquette `10` §4.4).
- Permissions de tous les agents qui écrivent : refuser `git checkout -- *`, `git checkout <ref> -- *`, `git restore*`, `git reset --hard*`, `git clean*`, `git stash drop*`/`clear` (coordonner le contenu exact avec T, propriétaire de `permissions/`).
- Récap complet (A35) : lignes **Checkpoints** (comportement selon le mode, obligatoires), **Beads autorisés**, **Code Mode**.
- Tests : `oh run ticket` sur un dossier modifié → worktree créé, fichiers de l'utilisateur intacts ; fiche (SimulationScreen).

### L2 — Épopées (A24)
- `--tickets <épopée>` : une session par ticket enfant ouvert (sauf `--one-session`), comme la fiche ; récap qui liste les enfants.

### L3 — Coûts, résultats et budget (A21, A22, A23)
- Coût d'une session = racine + sous-sessions (registre d'usage `usage_sessions`) partout : `oh session list`, vue Sessions, détail, résultats, accueils.
- `oh session results` (et récap de fin) : diff **de toute la session** (depuis le commit de départ de la session ou la base de la branche), coût total, **description de MR** (P3-T11).
- Après `oh budget raise` / touche `$` : **reprendre l'étape interrompue** (renvoyer le dernier tour, ou consigne de reprise par l'état de session) ; état `idle`/`active`, jamais `waiting` sans décision ouverte.

### L4 — État de session et réservations (A29, A31)
- État de session (S8) posé **avant** le premier prompt (à la création), jamais d'écriture qui réveille l'agent à la fin de son tour ; pas d'entrée `oh.checkpoints` pour un workflow sans checkpoint ; après un relèvement, valeur à jour dès le tour suivant.
- Réservations d'équipe : libérer (ou passer « terminée ») la réservation quand le ticket est fermé ou que la session se termine/s'arrête ; nettoyage des réservations orphelines (Doctor).
