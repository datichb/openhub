**Conséquences pour N3/N10 (ajustement des motifs proposé et appliqué)** :
1. Les gardes **doivent** commencer par `*` (préfixe d'environnement, `env`, `sh -c '…'`, `git -c k=v …`) — déjà le cas de `HookGuard`, `lockPatterns`.
2. Les gardes sur des **noms de variables** (`*GIT_DIR*`, `*GIT_CONFIG*`) sont contournables par `export GIT_DIR=… && git …` (déclaration non vérifiée) : gardées comme garde-fou contre l'erreur, documentées dans SECURITY comme non-barrière. 3. U2 négatif : les motifs sont contournables par guillemets/espaces → SECURITY le dit (« garde-fous, pas barrières »).
4. U4 : `external_directory` ne protège pas l'écriture hors du projet par le shell → les fichiers sensibles hors projet (`~/.zshenv`, `~/.ssh`, `~/.oh/run`…) ne sont protégés que par les motifs de la couche globale (N3), donc contre l'erreur seulement.

6. Motifs de verrou (N10, piste W) : l'ancrage sur la sous-commande (`git commit*`, `* git commit*`…) perdrait `sh -c 'git commit'` et `X=1 git commit` ; la forme `*git*commit*` reste la plus sûre. ## N1 — Passage d'un checkpoint sans l'utilisateur (DC1)

**Revérifié** : `POST /v1/workflow/checkpoint` sans garde ; `pass()` posait `By = "mode"` (ou `tool` si `Waiting == id`) sans aucune approbation → curl au socket = cp-2 passé, commit déverrouillé. Confirmé.

**Fait** :
- `checkpoint.Service.pass()` : un checkpoint dont le comportement est `pause`/`conditional` dans le mode exige `Approved[id]` ; sinon `ErrNotApproved` (409 + message traduit `cmd.daemon.workflow.not_approved` renvoyé à l'agent par le serveur MCP). Attente bornée (`ApprovalWait`, 3 s) tant que le checkpoint est `Waiting`, pour la course entre l'événement de réponse et l'appel MCP.
- **Écart (forme)** : pas de nouveau champ `ToolApproved` ; l'approbation observée dans l'outil est rangée dans `Approved[id]` avec `By = "tool"` (`Service.ToolReplied`), sans écraser une validation d'oh (qui porte le message). Même effet, aucun changement de schéma JSON.
- Adaptateur (D19) : `permission.replied` décodé (`{sessionID, requestID, reply}`, vérifié dans le source 2.0.20 et en e2e) en forme neutre **`adapters.DecisionAnswer{ID, Approved}`** portée par `ToolEvent.Answer` (le nom `DecisionReply` existait déjà pour l'envoi d'une réponse). Le démon (`watcher.onAnswer`) retrouve la décision ⏸ par `DecisionID(checkpoint, racine, requestID)`.
- Repli « interroger `GET …/permission` » **non fait** : une demande disparue ne dit pas si elle a été acceptée ou refusée (un refus la fait aussi disparaître) ; le repli serait contournable. Si l'événement est perdu (reconnexion SSE), l'appel est refusé et l'agent redemande : la validation est redemandée à l'utilisateur (sûr, un peu moins confortable). Documenté.
- **Réponse « always »** de l'interface de l'outil : enregistrée par opencode, elle laissait les checkpoints suivants s'exécuter sans demande (puis, avec N1, sans validation → impasse). Le plugin relaie désormais aussi les `allow` des actions `gated` (`workflow_checkpoint`) et `Evaluate` répond `ask` pour un checkpoint en pause.
- Routes : `/v1/workflow/{status,checkpoint,outputs}` authentifiées par le jeton du groupe (`Authorization: Bearer`) ; la session racine doit appartenir au groupe (401/403). Le jeton arrive au serveur MCP `workflow` par la variable neutre **`OH_GROUP_TOKEN`** (`sessionspec.EnvGroupToken`) posée par l'adaptateur dans l'environnement du serveur de l'outil (hérité par les MCP locaux : `extendEnv` d'opencode) ; pour les serveurs MCP lancés par le démon (passerelle, conteneur), le démon émet un jeton `ohw_…` en mémoire. Sans capacité configurée (tests, job distant), routes non gardées comme `privileged`. `/v1/workflow/rules`, `/groups/{g}/policy`, `GET /v1/clients` → `privileged` (la CLI charge la capacité pour `WorkflowRefresh`) ; TTL des battements ≤ 300 s.
- `credproxy.Proxy.Owner` ajouté (petite méthode exportée, zone de G : à signaler au rebase).
- Une session lancée par une version précédente d'oh (serveur MCP sans jeton) reçoit 401 : la relancer (CHANGELOG).

**Tests** : `TestPausedCheckpointNeedsAValidation`, `TestEvaluateAsksForAPausedCheckpoint` (service) ; `TestWorkflowRoutesNeedTheGroupToken`, `TestHeartbeatTTLIsBounded`, `TestWorkflowLocksAndEnd` (curl simulé refusé 409, puis demande + réponse observée → passe) ; `TestPermissionAnswer` (adaptateur) ; e2e Haiku `TestE2ECheckpointSocketBypassRefused` (curl de l'agent → 401, cp-2 non passé, commit refusé ; puis réponse `once` par l'API → passé `By=tool`, `commit` déverrouillé) — **vert** ; harnais e2e du workflow désormais gardé par une capacité (comme en production), `TestE2ECheckpointGating`, `TestE2EWorkflowCheckpointAsked` (passé sur `startGroup`) verts.
