### D3 — P4-T03, P4-T04
- **Spec du conteneur** (`container.Spec`, enregistrée dans `~/.oh/servers/<groupe>/container.json`) : paquet → `/opt/oh/bundle` (lecture seule), données → `/opt/oh/data`, projet et locations → `/work/<nom>` (suffixe `-2`… en cas de collision ; une location sous un dossier déjà monté n'est pas remontée), `/opt/oh/home` = volume nommé par projet (`HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` : la config opencode de l'utilisateur n'est jamais visible). Volumes de cache `Group.Volumes` : chemin absolu, ou relatif à chaque location montée (ex. `node_modules`).
- **Worktrees** : le dossier git commun d'une worktree liée (lu dans `.git` + `commondir`, sans binaire git) est **aussi monté à son chemin machine**, pour que les liens `gitdir:` absolus fonctionnent ; les liens relatifs (`--relative-paths`) fonctionnent si les worktrees sont des dossiers frères du projet (même nom de base sous `/work`). `GIT_CONFIG_*` : `safe.directory=*` et **`gc.worktreePruneExpire=never`** (un `git gc` dans le conteneur ne doit pas supprimer les métadonnées de worktrees qu'il ne voit pas).
- **Utilisateur** : Podman rootless `--userns=keep-id:uid=<uid>,gid=<gid>` (le gid par défaut de keep-id était 1000), sinon `--user <uid>:<gid>`. La couche fine crée `/opt/oh/{bundle,data,home}` et `/work` (`home` et `work` en 1777) ⇒ `layerVersion` = 2.
- **Sources partagées avec la VM** : refus explicite d'un montage hors des dossiers partagés (Colima : `$HOME` ; Podman machine : `/Users`, `/private`, `/var/folders` ; Docker Desktop : défauts) — sans ce contrôle, Colima monte un **dossier vide** en silence.
- **Environnement** : les variables du conteneur passent par un fichier `--env-file` (0600, `~/.oh/servers/<groupe>/container.env`, réécrit à chaque lancement), jamais en ligne de commande ni mêlées à l'environnement du CLI (`-e NOM` aurait écrasé `HOME` du CLI docker → contexte Colima introuvable). Le CLI ne reçoit qu'une liste blanche (`PATH`, `HOME`, `DOCKER_*`, `CONTAINER_*`…). Valeur avec retour à la ligne ⇒ erreur.
- **Réseau** : ports publiés sur `127.0.0.1` uniquement ; `--add-host host.docker.internal:host-gateway` pour Docker sous Linux. Linux (moteur sans VM) : `Prepare` résout l'adresse de la machine **depuis un conteneur** (`getent hosts`) → `Prepared.ListenHost` ; le démon ajoute une écoute du proxy sur cette IP (`POST /v1/proxy/listeners`, même port si libre, IP privée ou de bouclage seulement, persistée dans `ohd.json` et restaurée au redémarrage). Non testé en réel (machine de build macOS).
- **Processus** : `Command` = `<cli> run --rm --init --name oh-<groupe> …` attaché (le PID suivi par oh est celui du CLI ; un signal est relayé au conteneur) ; un conteneur résiduel du même nom est supprimé avant ; `Teardown` = `rm -f`.
- Validé en réel (`TestRealMountsAndNetwork`, Colima et Podman) : `git status` dans la worktree depuis le conteneur, fichier créé appartenant à l'uid de l'utilisateur, paquet non inscriptible, aucun secret dans `env` (variable AWS présente côté machine), service `127.0.0.1` de la machine joint via `HostAddress`.

L'URL du groupe est gardée dans `~/.oh/servers/<groupe>/gateway_url` et transmise au crochet (`SessionEnvRequest.GatewayURL`, plus `Runtime`, `WorkflowID`, `BeadsAllow`). Remarque : dans ce test, le jeton du proxy (`AWS_BEARER_TOKEN_BEDROCK`) n'apparaissait pas non plus dans le shell de l'agent (non vérifié sans environnement de session).
- **Constat opencode 2.0.20 (sous-agents)** : l'environnement de session **n'est pas transmis** aux sous-sessions lancées par l'outil `task` (e2e `TestE2ESubagentSessionEnvironment`, qui échouera le jour où ce sera le cas). Repli retenu : quand le démon rattache une sous-session à sa racine (`adoptChild`, en direct ou à la resynchronisation), il lui applique l'environnement de la racine : `env.json` statique, `OH_SESSION_ID` de la racine, et pour le conteneur `OH_GATEWAY_URL` plus un jeton propre à la sous-session (`Grant.Holder`).
